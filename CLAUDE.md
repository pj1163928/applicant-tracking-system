# CLAUDE.md

An internal, staff-only Django applicant tracking system for CIDM 3312; candidates never log in.

## Stack
- Python, Django, SQLite, Tailwind CSS + DaisyUI via django-tailwind-cli, HTMX, Ruff, Pytest with pytest-django. All required.
- Package manager: **uv**.
- Email goes through Django's mail framework: console backend in development, locmem in tests.

## Architecture decisions (from the PRD)
- Roles are Django Groups (Recruiter, Hiring Manager, Interviewer); Admin is `is_superuser`. No self-registration.
- Every role can view everything; Interviewers are view-only. Ownership changes default filters and labels, never visibility.
- Permission rules live in pure, separately testable functions. Views and templates call them; they don't duplicate the logic.
- Stage rules live in a pure module (allowed-transitions table, `can_move`, `requires_note`).
- Business logic lives in service functions, not views. `move_application()` is the only way an application's stage changes. That includes the seed and every later closure, cancel and restore flow.
- Illegal actions are refused on the server even when the UI already hides them.
- Partial page updates use HTMX; drag-and-drop uses the browser's own pointer events (no SortableJS or other drag library), so it works with a mouse and on touch screens.
- Sources and skills are retired, not deleted; foreign keys to them use PROTECT.

## Conventions
- Settings live in `config/`. Each owning app (`accounts`, `candidates`, `openings`, `applications`, `notifications`) has its own models, views, `templates/<app>/` and `tests/`. Shared templates (`base.html`, `registration/`) are in `templates/`.
- Forms mix in `config.forms.DaisyUIFormMixin` for DaisyUI widget classes and invalid-input marking; list per-field classes in `CLASSES`, written out in full.
- Views are thin and class-based. Logic goes in models and managers, and cross-model workflows go in a `services.py`. Every public function in a deep module gets a docstring and type hints.
- Every URL is named and app-namespaced (`app_name = "..."`), and records are addressed by pk. Sources live in the `candidates` app but have their own `sources:` namespace at `/sources/`; skills likewise live in `openings` with a `skills:` namespace at `/skills/`, and so does the Admin in-progress view (`in_progress:list` at `/in-progress/`).
- `LoginRequiredMiddleware` makes every view need a login. Only the login page is exempt.
- Roles: use `accounts.roles` (`has_role`, `can_make_changes`, `role_label`, and the `RECRUITER`/`HIRING_MANAGER`/`INTERVIEWER` constants). Never check group names inline.
- Action rules live in `accounts.permissions`: a roles tuple plus a `can_<action>(user)` function (e.g. `CANDIDATE_MANAGER_ROLES`, `can_manage_candidates`, which covers archiving too; `CANDIDATE_DELETER_ROLES = ()`, `can_delete_candidates`, Admins only; `SOURCE_MANAGER_ROLES`, `can_manage_sources`; `OPENING_MANAGER_ROLES`, `can_manage_openings`, which covers closing and reopening too; `APPLICATION_MANAGER_ROLES`, `can_manage_applications`; `STAGE_MOVER_ROLES`, `can_move_applications`; `SKILL_RETIRER_ROLES`, `can_retire_skills`; `IN_PROGRESS_VIEWER_ROLES = ()`, `can_view_in_progress`, Admins only). Views pass the tuple as `allowed_roles`; templates use the matching `accounts_tags` filter.
- Per-opening rules take the opening too. `can_make_offer(user, opening)` (moves into Offer or Hired) is an active Admin, an active Hiring Manager, or the opening's designated authority while `can_be_designated_authority()` still holds for them. `is_staff` and move rights never grant it. `can_manage_opening_skills(user, opening)` (attach, detach, create inline) is the same three. Both use `is_eligible_authority_of(user, opening)` for the authority part, so authority covers that one opening only. Retiring skills is the role-only `can_retire_skills` (Admins, Hiring Managers), which authority never grants. `can_decide_closure(user, opening)` (cancel now, grace periods, and restoring after a reopen) is the same three again, with `CLOSURE_DECIDER_ROLES = (HIRING_MANAGER,)`: a Recruiter who isn't the authority can close or reopen an opening but never decide.
- Designated authorities: `can_be_designated_authority(user)` and `eligible_authorities()` in `accounts.permissions` (active Admins, Recruiters and Hiring Managers). Any field that picks an authority uses `eligible_authorities()` as its queryset, so the same query lists the choices and validates the submitted pk; a hand-made POST naming anyone else fails validation.
- Applications are created only by `applications.services.record_application()`, which locks and re-reads the candidate, checks `application_refusal()` (archived candidate, closed opening, duplicate; later phases add reasons) and writes the application plus its first StageChange row (no stage → Applied) atomically. Forms call `application_refusal()` for the same message. The Django admin shows applications and stage history read-only. `Application.save()` clears `referred_by` unless the source is a Referral.
- Stage rules are pure functions in `applications.stages`, taking stages only, never the database, a user or a request: `ALLOWED_TRANSITIONS`, `can_move`, `requires_note` (the move can't be made without a note), `prompts_for_note` (the note dialog opens: required, or optional for Rejected and Withdrawn), `move_kind`, `skipped_stages`, and `move_targets(from_stage, may_offer=...)` for menus. The note helpers raise `ValueError` for an illegal move.
- Stages change only through `applications.services.move_application(application, to_stage, *, by, note, cause, expected_stage, closure)`. It locks and re-reads the row, checks `move_refusal()` (role, stale card, archived candidate, table, `can_make_offer`) and the note, and then writes one StageChange row plus the cached stage atomically. Any UI that moves a card passes `expected_stage` (the stage the card showed), so a stale card or a double submission is refused, not applied. Views call `move_refusal()` with the same arguments before opening a note dialog.
- The board (`applications.board.board_columns`) builds both the full board and the endpoint's partial columns. The single move endpoint (`applications:move`) answers HTMX with a message for `#board-status`, plus out-of-band `innerHTML` swaps of `#count-<stage>` and `#cards-<stage>` for the affected columns only. Refusals are 400 (rules) or 403 (permission), with the same fragment; the board's script lets HTMX swap those. Note and history dialogs arrive in `#dialog-slot` (`HX-Retarget`), and the board opens them with `showModal()`. Without HTMX the endpoint redirects, or renders a page.
- Drag-and-drop posts each card's hidden drop form (`data-drop-form`, carrying `expected_stage` and `dropped`) to that same endpoint, so drops and the Move menu get the same rules and refusals. A legal drop always gets a dialog before anything moves: the note dialog when the move asks for a note, otherwise a plain confirmation (`dropped` exists because a drop is easy to make by accident). A Move-menu one-step move still happens at once. Only cards with Move targets can be picked up (no `draggable` attribute: the board's script handles `pointerdown`, with press-and-hold on touch). `data-move-targets` and `data-note-targets` (from `Column.drop_stages`/`note_stages`) only light up columns; a drop on any other column is posted anyway, so the server refuses it with its message. While a dropped card waits for the dialog it sits in its new column; closing the dialog sends it home, and any other answer puts it back before the server's columns are swapped in. The board lays out without horizontal scrolling: the pipeline stages in a grid with arrows (`partials/stage_arrow.html`), and Rejected and Withdrawn apart below it, all inside `data-drop-area`. Drag styles live in `assets/css/source.css` (`.drop-target[data-drop…]`, `.drag-float`, `.drag-slot`, `.drop-gap`, `.drop-pending`), with no text hints in the columns, and after a move the endpoint marks the moved card `animate-land` (`landed_pk`) or the refused one `animate-shake` (`bounced_pk`). The chosen design is variant B of [prototypes/board-drag-feel.html](prototypes/board-drag-feel.html).
- Board cards are newest first (`-updated_at`), so a moved card goes to the top and the drop gap opens there. A column with more than `applications.board.FOLD_AT` (3) cards folds: `column_cards.html` marks the rest `data-beyond-fold` and renders a "+N more · Show all" toggle, and the board's script sets `data-expanded` on the column to show them, with a name search (`partials/stage_search.html`, outside the swapped `<ul>` so typing survives a move). After every HTMX settle the script re-applies each column's expanded state and search to the new cards. An empty column shows an icon, stretched to match its row up to about three cards. Check drag-and-drop by hand with [docs/MANUAL_CHECKS.md](docs/MANUAL_CHECKS.md).
- Candidates are archived and unarchived only through `candidates.services.archive_candidate(candidate, *, by)` and `unarchive_candidate(...)`, which check `can_manage_candidates`. Archiving sets `is_archived` and `archived_at` together (a check constraint keeps them in step) and is refused by `archive_refusal()` while any application is at an active stage. Archived candidates leave `Candidate.objects.unarchived()` (the list's default and the application form's queryset) but keep their applications on boards and opening pages, with an "Archived" badge (`candidates/partials/archived_badge.html`). Their cards have no Move controls: `board_columns` sets each card's `movable`. Permanent delete goes only through `delete_candidate(candidate, *, by)` (`can_delete_candidates`), from a confirmation page built from `deletion_summary()`. The Django admin shows the archive fields read-only and lets only Admins delete.
- Openings close only through `openings.services.close_opening(opening, *, by, note)` (`can_manage_openings`), which locks the row, sets the status, writes a "closed" `OpeningEvent` and, if any application is active, emails the designated authority. The opening forms have no `status` field and the Django admin shows it read-only, so nothing else can close (or reopen) one. Closed openings refuse new applications but their applications keep moving, Offer and Hired included. `cancel_remaining_applications(opening, *, by)` (`can_decide_closure`, closed openings only, checked by `cancel_refusal()` before any application changes) moves every active application to Rejected through `move_application(..., cause=CLOSURE, note=CLOSURE_NOTE)`, emails each candidate, and writes one "Remaining applications cancelled" event per closure, all in one transaction. It is safe to repeat: with nothing active it changes nothing. `OpeningEvent` rows are written only by these services and listed on the opening page (`openings/partials/event_history.html`); the closure panel (`partials/closure_panel.html`) shows while a closed opening has active applications.
- Grace periods change only through `openings.services.set_grace_period(opening, *, days, action, by, today=None)` (1–90 days, once per closure, emails each active candidate) and `extend_grace_period(opening, *, ends, note, by, today=None)` (note required, no email, refused after an auto-cancel end), both `can_decide_closure`. Dates are calendar days in `America/Chicago`; services take `today` (default `timezone.localdate()`) and the schedule rules in the pure `openings.grace` (`due_reminder`, `grace_period_has_ended`, which is `today >= ends`) never read the clock. The daily `process_grace_periods` command (`--today YYYY-MM-DD` for demos) calls `process_grace_periods(today=…)`: one locked transaction per opening, reminders keyed on closure + end date + days left, and on the end date `expire_grace_period()` sets `grace_expired_on` (so the end runs once), writes "Grace period ended", then auto-cancels through `cancel_remaining_applications` or emails the authority (`notify_authority_of_overdue`). The four `JobOpening.grace_*` fields are kept in step by a check constraint and are read-only in the admin. Confirmation pages for set and extend share `ClosureDeciderMixin` with cancel now.
- Candidate emails go only through `notifications.services.send_candidate_message(application, kind, *, occasion, context=None)`. It renders `notifications/email/<kind>_subject.txt` and `_body.txt`, logs a `CandidateMessage` and sends after commit (`transaction.on_commit`), so a rolled-back change emails nobody. Its identity is (application, kind, occasion), unique in the database, and a repeat returns None without sending. A cancellation's occasion is its closure (`closure-<closed event pk>`). Staff emails (`notify_authority_of_closure`) also send after commit. Candidate emails say "our team will be in touch to complete the next step"; normal rejections and hires send none.
- The Needs attention panel (`notifications:attention`, `/attention/`) lists `notifications.attention.closures_awaiting_decision(user)` plus `restores_awaiting_choice(user)` (each item's `kind` picks its partial in `partials/attention_entry.html`): closed openings with active applications and no grace period running (`JobOpening.objects.awaiting_closure_decision()`, annotated `active_count`; overdue ones included, with an "Overdue" badge) that the user may decide, theirs first. The nav badge counts only those where the user is the authority (`attention_summary(user).yours`, which is `attention_count`); its breakdown adds `others`, the ones an Admin or Hiring Manager may decide for someone else.
- The Admin in-progress view (`openings.views.InProgressView`, `allowed_roles = IN_PROGRESS_VIEWER_ROLES`) lists `openings.in_progress.in_progress_openings(today=None)`: every `JobOpening.objects.closed_with_active_applications()` (annotated `active_count`, which `awaiting_closure_decision()` builds on), Overdue first, then Awaiting decision, then In grace period. Each status comes from the pure `openings.grace.closure_status(ends=, action=, expired_on=, today=)`: Awaiting decision with no grace period or after an auto-cancel the daily run has done; In grace period while `today < ends`; Overdue from the end date itself for flag overdue, and for auto-cancel until the run has cancelled, so a late or missed run shows. It uses today's date, so on the end date it can say Overdue before the closure panel and Needs attention (which read the stored `grace_expired_on`) do. Only Admins see its nav link, whose badge counts Overdue + Awaiting decision (`in_progress_counts().to_act_on`, red when anything is overdue; In grace period isn't counted).
- Nav counts: `base.html` works them out once, `{% attention_summary user as attention %}` (`notifications_tags`) and, for Admins, `{% in_progress_counts as progress %}` (`openings/templatetags/in_progress_tags.py`), and `partials/nav_links.html` reads both. Each count-carrying link is a `group` holding a `.nav-popup` (the top bar's hover/focus breakdown, `aria-hidden`, lg and up) and a `.nav-breakdown` line (the sidebar's, below lg), styled in `assets/css/source.css`. Count with queries, never by listing every opening on each page.
- Openings reopen only through `openings.services.reopen_opening(opening, *, by, note)` (`can_manage_openings`, so anyone who may close it), which locks the row, sets it open, clears all four `grace_*` fields (so reminders and the end stop) and writes a "reopened" event. Cancelled applicants come back only through `restore_applications(opening, applications, *, by)` (`can_decide_closure`, open openings only): each goes back to the `from_stage` of its cancellation row through `move_application(..., cause=REOPENING, note=REOPEN_NOTE, expected_stage=REJECTED, closure=…)`, its candidate gets one `restored` email (occasion `closure-<pk>`), and one "Applicants restored" event is written, even for "Don't restore anyone". It checks every chosen application first (`application_restore_refusal()`, built on `move_refusal()`, so Offer still needs `can_make_offer` and archived candidates are refused) and is all or nothing. Every cancellation and restore row names its closure (`StageChange.closure`, the "closed" `OpeningEvent`; manual rows never do, by a check constraint), and `restorable_cancellations(opening)` is the latest closure's cancellations whose application hasn't moved since (`StageChange.objects.cancellations_to_restore()`). The checklist is `restore_choices(opening, by)` (`RestoreChoice.refusal`: "Archived; unarchive first", or offer authority), and `RestoreApplicationsForm` takes its queryset from the selectable ones. `JobOpening.objects.awaiting_restore_choice()` (annotated `restorable_count`) is a reopened opening with restorable applicants and no "Applicants restored" event since the reopening; Needs attention lists it (`restores_awaiting_choice`, `RestoreItem`) and the nav badge counts it, and the opening page shows `partials/restore_panel.html`.
- An opening's skills change only through `openings.services.attach_skill(opening, name, *, by)` and `detach_skill(opening, skill, *, by)`, which check `can_manage_opening_skills`. Attaching finds the skill by name ignoring capitals and extra spaces (`Skill.objects.named()`), creates it only if none matches, and refuses retired or already-listed skills. Openings and skills are joined through `OpeningSkill` (PROTECT on the skill). Seed is the one exception: it links skills directly to recreate a retired skill already on an opening.
- Choice fields that encode a rule take their queryset from the rule: candidates who may apply from `Candidate.objects.unarchived()`, open openings from `JobOpening.objects.accepting_applications()`, new-application sources from `Source.objects.active()`, and an existing application's sources from `Source.objects.active_or_current(its_source)`.
- Views that change data use `accounts.mixins.RoleRequiredMixin`. It returns 403 to Interviewers by default; set `allowed_roles` to narrow it.
- Templates load `accounts_tags` (`user|role_label`, `user|can_make_changes`, `user|can_manage_candidates`, `user|can_delete_candidates`, `user|can_manage_sources`, `user|can_manage_openings`, `user|can_manage_applications`, `user|can_move_applications`, `user|can_make_offer:opening`, `user|can_manage_opening_skills:opening`, `user|can_retire_skills`, `user|can_decide_closure:opening`, `user|can_view_in_progress`) to hide actions, and the server still enforces the rule.
- UI uses DaisyUI v5 classes (`fieldset`, `input`, `btn`, …), with the `corporate` (light) and `business` (dark) themes. HTMX is loaded in `skeleton.html` and sends the CSRF token through `hx-headers`. Views that return a fragment for HTMX check `config.htmx.is_htmx_partial(request)` (full page for history restores) and send `Vary: HX-Request`.
- Templates: staff pages extend `base.html`, which has a top nav on `lg` and up and a drawer sidebar below that. Pages without navigation (login) extend `skeleton.html`. Each new section adds one `<li>` to `templates/partials/nav_links.html`, which feeds both menus.
- `skeleton.html` links the built CSS with `{% tailwind_stylesheet %}` (`config/templatetags/stylesheets.py`, registered by name in `TEMPLATES`), not the library's `{% tailwind_css %}`: it adds `?v=<file modification time>`, so a rebuild gets a new address and no browser (VS Code's built-in one especially) keeps a stale copy.
- Icons: `{% icon "name" "size-5" %}` is a builtin, so no `{% load %}` is needed. It inlines `templates/icons/<name>.svg`, copied from lucide-static v1.49.0. Add an icon by copying its SVG there.
- Motion stays subtle: `animate-rise`, `animate-land`, `animate-shake` and `animate-gap` (defined in `assets/css/source.css`) and hover transitions, always paired with `motion-reduce:` fallbacks. Layouts must work from 360px phones to desktop.
- `seed` (`accounts/management/commands/seed.py`) is idempotent. Each phase adds data by natural key, and a second run must change nothing. Seed never undoes a deliberate staff change to a record's state (for example, it doesn't reactivate a retired source, and closes a seeded opening only in the run that creates it). Every seeded user has the password `demo-pass-123`.
